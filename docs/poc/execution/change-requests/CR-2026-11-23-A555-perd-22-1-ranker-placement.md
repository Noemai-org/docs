- The Architect's answers (rulings A559 for questions 1 and 2, A560 for questions 3 and 4; Interim, relayed 23 Nov 2026; refined by A566):
  1. **A559 (Q1): does the Python ranker stay in production?** Only if it has a caller. The Trust T7 ranking uses the Go port. C2 says whether `understanding/resolution/ranking.py` has any production caller. If none, it stops being a production code path and stays only as the reference implementation that generates the parity vectors. If it has a caller, that caller may use it only for a non-authoritative ordering, for example to present options.
  2. **A559 (Q2): which is authoritative if they differ?** The Go port in Trust. Model-service output is untrusted data (INV-02), and Trust never accepts a ranking it did not compute itself. A difference is a failing parity test, never a runtime choice.
  3. **A560 (Q3): the Rank row's owner column.** The PERD row changes from "Understanding" to "Trust (deterministic code, no model)", with a note that Understanding keeps a non-authoritative reference. It goes in this change request, which stays a Draft until the Founder adopts it. Nothing in the PERD is edited in place.
  4. **A560 (Q4): numeric semantics.** Scores are integer basis points, using floor division, never floating point, in both implementations (A462). The thresholds keep their values in the same unit: the 0.35 margin is 3500 and the 0.70 floor is 7000, in pack or limits data, never in code constants (AGENT-16). Where rounding could matter, it rounds against acting: a score that is uncertain falls below the floor and ends in CLARIFY. The parity vectors cover just below, exactly at and just above both thresholds, in a single shared vector file that both test suites load. A change to either implementation needs the file to pass in both.
- Proposed PERD text, once the Founder adopts this request (for the new version file): "Ranking is deterministic code, not a model call [REC]. The ranker is a pure function of candidate fields, slot values and pack weights, computed in integer basis points with floor division, so that rounding is against acting. The authoritative ranker is a Go implementation in Trust, and Trust never accepts a ranking it did not compute itself; the Python ranker is only the reference that generates the shared parity vectors, or, if it has a production caller, a non-authoritative ordering. The margin (3500) and the floor (7000) are pack or limits data. One shared vector file holds cases below, at and above both thresholds." The Rank row's Owner column reads "Trust (deterministic code, no model)", with a note that Understanding keeps a non-authoritative reference. The values (weights, 0.35 and 0.70) do not change; only their representation does.
- **The A566 exact-comparison rule (ruling A566, Interim, binding once `DEC-2026-11-23-architect-rulings-a561-a580` is approved and merged by a non-author Founder; refines A560 item 4).** Floor division applies only to the final reported score. The margin and the floor are compared in exact scaled-integer arithmetic on the unrounded sums, never on floored scores. A vector with a fractional score at the margin is required: top 9000.00 against 5500.25 must be AMBIGUOUS (the difference is 3499.75, below the 3500 margin; on floored scores it would read 3500 and pass).
- **Proposed PERD note for REQ-AMB-003 (for the new version file, with the A555 text above):** "Comparison rule [A566]: each candidate's score is the exact sum Σ wᵢ·fᵢ in scaled integers. The auto-resolve tests (`top − second ≥ auto_resolve_margin`, 3500, and `top ≥ 0.70`, 7000) are evaluated on the unrounded sums, never on floored scores. Floor division is applied only to the score that is reported and recorded. Where rounding could matter it rounds against acting. The shared vector file includes cases with a fractional score at the margin and at the floor, for example top 9000.00 against 5500.25, which is AMBIGUOUS."
- **Ties (ruling A583, Interim, binding once its record, `DEC-2026-11-23-architect-rulings-a581-a592`, is approved and merged by a non-author Founder).** A tie at the top means equal exact scaled sums; the margin is then 0, so the outcome is AMBIGUOUS. Proposed addition to the REQ-AMB-003 note: "A tie at the top (equal exact scaled sums) gives a margin of 0 and the outcome AMBIGUOUS." The shared vector file includes a tie case. (REQ-AMB-003 today says "a tie means CLARIFY"; AMBIGUOUS is the ranking result and Trust's decision follows REQ-AMB-003; C2 and C1 confirm that in the vectors.) **Acceptance for the Trust side (Codex, docs#234):** the ranker vector file proves the two rankers agree; it does not prove Trust's mapping. A separate integration test through the real T7 decision path with equal exact sums asserts: ranker result AMBIGUOUS, Trust disposition CLARIFY, no grant, and no candidate read beyond what the clarification flow permits. The security reviewer also looks for a tie at the top and a tie at the floor in the vector file.
- Acceptance the parity suite must meet: the shared vector file has cases just below, exactly at and just above **both** the margin (3500) and the floor (7000); every implementation that exists gives identical decisions on it. Identical inputs give identical scores (REQ-AMB-003).
