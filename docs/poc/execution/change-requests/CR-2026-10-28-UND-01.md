## Proposed acceptance tests for the later implementation task

- A valid request returns the §39.3 response shape with an Intent Object accepted by the active generated contract types.
- Malformed JSON, missing fields, unknown fields and oversize canonical text each return the active error envelope with a defined non-retryable error code. Use the existing catalogue only; proposed mapping is INPUT_INVALID for invalid request input and SCHEMA_INVALID for an invalid proposer output. Confirm the mapping against the active contract before implementation; add no error code or threshold.
- Replay each approved BDC-INJ case text from the frozen corpus as an input request, read-only. Preserve the corpus bytes and do not edit benchmark/. No result may be represented as authorized or safe to execute.
- Load the same pack and process the same input twice; assert byte-identical normalized pack/pipeline result and response.
- Use canned proposers only. No keys are needed by these tests. Do not read held-out cases or oracle material.

**Meaning of the BDC-INJ acceptance:** Understanding emits a proposal; schema validity does not mean authorization or safety to execute. PERD §20 and the UND-05 card require a prohibited requested remedy to remain an explicit slot/reference for Trust to reject through the registry. The phrase “no proposal that passes validation as a safe action” must therefore mean that no output is marked authorized/ALLOW or can reach Execution. If the requester instead requires the model endpoint to suppress every schema-valid proposal whenever BDC-INJ text appears, that would conflict with the proposal-only boundary and the current UND-05 semantics. The Engineering Lead and Founder must resolve that wording before the implementation task starts.
