# Change request: CR-2026-11-18-A216-planned-to-escalating

- Change ID: CR-2026-11-18-A216-planned-to-escalating
- Requester: Engineering Lead (EL), at the Founders' order of 18 Nov 2026 (A317 to A328, relayed, not yet committed): "the PLANNED to ESCALATING CR and the runner test". Follow-up of noema#576 and noema#678 (A216, A217).
- REQ IDs affected: REQ-RCV-003 (recovery budget and escalation), REQ-STM-001 (the investigation state machine, PERD §28.2). Plan tasks: STM-01 (the write runner).
- Behaviour before (evidence: noema `services/core/orchestrator/runwrite.go`, the `ReceiptBudgetSpent` case and the `exhausted` case before `move("PLANNED")`; `transitions.yaml`, which has no arrow from PLANNED to a hand-over state): when the database refuses a dispatch because the logical key's budget is spent (A153), or Trust allows another write although the budget is used up, the runner returns `ErrRecoveryBudgetSpent` and records nothing. In the second case the investigation stays in EVALUATING; in the first it stays in PLANNED, which the public stage map shows as "working". The customer is told the work goes on, and nobody is handed the case. REQ-RCV-003 makes ESCALATE the result at the limit.
- Behaviour after (the arrow as ordered): PERD §28.2 gains one arrow, PLANNED to ESCALATING, on "dispatch budget spent (REQ-RCV-003)". The runner takes it when the Executor reports `ReceiptBudgetSpent`, and then stops with `ErrRecoveryBudgetSpent`. The grant that was issued is never spent and expires by TTL. A runner test pins it: the move is recorded once, nothing is verified, nothing is dispatched again.
- Safety and security impact: no Tier 0 gate, threshold, TTL or budget changes (the limit stays PERD's 2, AGENT-16). The change only adds a way out of a stuck "working" state. **One principle needs the Architect's reading:** §28.2 says every transition is caused by, and cites, a Record event and a power's signed object. The existing way into ESCALATING cites a Trust DECISION_MADE ESCALATE. An arrow from PLANNED that the runner takes by itself cites no Trust decision, so it would be the first transition made without one. Two ways to meet it: (a) the arrow's cited event is the Execution Controller's refusal event (the budget-spent receipt) and §28.2 says so; or (b) no new arrow, see the alternative below.
- Alternative for the Architect (smaller, no PERD change): on `ReceiptBudgetSpent` the runner takes the existing arrow PLANNED to EVALUATING (the "grant voided" path: nothing was dispatched), and asks Trust again. Since noema#572 Trust itself decides ESCALATE `DISPATCH_BUDGET_EXHAUSTED` at T12 (A224, A254), so the existing arrow EVALUATING to ESCALATING follows with a recorded Trust decision and no new arrow. A216 ruled against evaluating again at the time it was written, when T12 did not yet decide it. EL recommends this alternative unless the Architect confirms that the budget-spent refusal is itself a signed object that may cause the transition.
- Tests added or changed: a runner test (noema, EL), failing first (AGENT-11), written against whichever option is decided; none is weakened, skipped or deleted. None here.
- Schedule and dependency impact: none on gates. The test and the arrow wait for the decision; until then the runner behaves as today.
- SoT or PERD text changes: option (b) was chosen: none. (Option (a) would have been:, a new PERD version file for §28.2, with the decision record, the vendored extract and the regenerated register in one PR (AGENT-29). Option (b): no.)
- **Decided (the Founders, 19 Nov 2026, A341 to A357, interim, relayed, not yet committed): OPTION (b), no new arrow.** On `ReceiptBudgetSpent` the runner takes the existing arrow PLANNED to EVALUATING and asks Trust again; Trust's own T12 decides ESCALATE `DISPATCH_BUDGET_EXHAUSTED` (noema#572, A224, A254), and the existing arrow EVALUATING to ESCALATING follows with a recorded Trust decision. PERD §28.2 is unchanged. The code is noema `feat/STM-01-budget-spent-reevaluates` (tests first).
- Decision owner: Principal Architect
- Decision record: to be written with the decision (DEC-2026-11-…).
- Migration and rollback: option (a) adds one row to `transitions.yaml` and the vendored §28.2 extract, in the same PR as the runner change; roll back by removing the row and the runner case. Option (b) changes only the runner (one `move` and one `evaluate` call in the `ReceiptBudgetSpent` case); roll back by restoring the stop.
