# Change request: CR-2026-11-19-T13-decline-reject

- Change ID: CR-2026-11-19-T13-decline-reject
- Requester: Engineering Lead (EL), at the Founders' decision of 19 Nov 2026 (relayed, not yet committed): "Build the Declined-to-REJECT path now. This is founders decision."
- REQ IDs affected: REQ-TRU-002 (the fixed step order and the outcomes each step may end with), REQ-AMB-004 (confirmation), INV-25. Plan task: TRU-12.
- Behaviour before (evidence): PERD §23.3's step table gives T13 (Confirmation requirement) the terminal outcome CONFIRM only. `trust/decide/evaluate.go` `stepOutcomes` encodes it as `T13Confirmation: {Confirm}`, and `decide.Evaluate` accepts a Stop only if the step allows that outcome, so a REJECT at T13 ends UNKNOWN INTERNAL_ERROR. SoT §43.2a (item 4) says the opposite for the same event: "On `DECLINE`, the decision closes as REJECT with reason `DECLINED_BY_APPROVER`." The conflict is not in the conflicts register (checked 19 Nov 2026). Until this CR, a decline fails closed to UNKNOWN (AGENT-20).
- Behaviour after: T13 may end in CONFIRM or REJECT. A declined confirmation ends the evaluation in REJECT with the core reason code `DECLINED_BY_APPROVER` (already in the closed reason enum), carrying the basis of the evaluation, with no new request opened, no plan, no Decision Record write of an ALLOW and no grant. The SoT is unchanged: it already says this.
- The text change for the next PERD version (a new version file, never an edit in place): in §23.3, the T13 row's terminal-result cell changes from "CONFIRM" to "CONFIRM, REJECT (DECLINED_BY_APPROVER on a declined confirmation, SoT §43.2a)". Nothing else in §23.3 changes; the reason code list already names DECLINED_BY_APPROVER.
- Safety and security impact: none of the Tier 0 gates, thresholds, TTLs or budgets change. A decline can only refuse; it can never authorise. The REJECT is reached only from an answer the Confirmations adapter has already checked (an authenticated approver, a request of this tenant and principal). INV-25 is untouched: a grant still follows only a valid ACCEPT that resolved to a fresh evaluation.
- Tests added or changed (noema#755, EL, failing first at `7c666fe9`): `TestT13MayEndInRejectDeclinedByApprover` (decide) and `TestT13DeclinedIsRejectDeclinedByApproverAndRecordsNothing` (intake) are new; the step-table expectation in `decide/evaluate_test.go` widens T13 to {CONFIRM, REJECT}; two intake tests that used the status value after Given as "unknown" now use the value after Declined. No test is weakened, skipped or deleted.
- Schedule and dependency impact: none on gates. The route that answers an approver (noema#754) and the confirmation store (migration 0032) are separate.
- SoT or PERD text changes: PERD §23.3 only (above): a new PERD version file, the decision record and the regenerated indexes move together in one PR (AGENT-29), made by the Steward. SoT: no.
- Decision owner: Founders (the decision is theirs; the PERD row is the Architect's text).
- Decision record: to be written with the next PERD version.
- Migration and rollback: apply with the next PERD version; roll back by restoring T13 to {CONFIRM} in `stepOutcomes` and removing the `ConfirmationDeclined` case (noema#755), after which a decline is UNKNOWN again.
