Integration Adapters

Status: Foundational
Version: 0.1
Domain: Integrations
Canonical Path: integrations/adapters.md

⸻

1. Definition

An Integration Adapter is the governed Noema execution boundary that translates canonical Noema operations into the protocol, API, data model, authentication mechanism, and operational semantics of an external enterprise system.

An adapter allows Noema to interact with enterprise systems without requiring the rest of Noema to understand provider-specific implementation details.

Conceptually:

Noema
  │
  │ Canonical Action Contract
  ▼
Integration Adapter
  │
  │ Provider-specific translation
  ▼
Enterprise System

The adapter is an implementation boundary. It does not redefine the canonical meaning of the Intent, Action, Capability, Trust Decision, Outcome, or enterprise Business State.

⸻

2. Purpose

Adapters exist to isolate external-system complexity from Noema’s canonical execution model.

They provide a controlled boundary for:

* capability binding
* protocol translation
* request transformation
* response normalization
* authentication
* credential handling
* authorization context propagation
* error translation
* timeout handling
* idempotency
* provider-specific constraints
* observability
* evidence production
* reconciliation
* provider event translation

⸻

3. Adapter Principle

An adapter is a translator and execution boundary, not a semantic decision-maker.

The adapter must not independently determine:

* user intent
* canonical Intent meaning
* Trust
* enterprise policy
* whether an action should be executed
* whether an ambiguous request should be guessed
* enterprise authorization
* whether an enterprise business fact should be redefined
* whether an alternative capability should be invented

Those decisions belong to the appropriate Noema contract, Trust, planning, graph, or enterprise authority.

Provider-specific enforcement may still reject an operation. Such rejection is provider execution behavior, not an invitation for the adapter to reinterpret the request.

⸻

4. Canonical Boundary

The adapter separates:

Canonical Noema Semantics
        │
        ▼
Hard Contract / Execution Boundary
        │
        ▼
Integration Adapter
        │
        ▼
Provider-Specific Semantics

The canonical side should remain stable even when the provider implementation changes.

Provider-specific changes should normally be absorbed through adapter configuration, mapping, or adapter versioning rather than silently changing canonical capability or action semantics.

⸻

5. Adapter Responsibilities

An adapter may be responsible for:

Capability Binding
Request Translation
Authentication
Credential Handling
Protocol Translation
Response Normalization
Error Mapping
Timeout Handling
Idempotency
Provider Constraints
Observability
Evidence Production
Reconciliation Support
Provider Event Translation

These responsibilities must remain explicit and bounded.

⸻

6. Non-Responsibilities

An adapter must not become an implicit location for:

* intent interpretation
* arbitrary business logic
* Trust decisions
* policy invention
* permission invention
* capability invention
* hidden business-level retries
* silent state mutation
* canonical business-state ownership
* model-generated execution decisions
* arbitrary HTTP or SQL generated by a model

An adapter that accumulates these responsibilities becomes an uncontrolled execution layer.

⸻

7. Hard Validation Boundary

An adapter must not be the first place where arbitrary model output or unvalidated external data becomes executable Noema semantics.

The canonical execution boundary is:

Source of Intent
      ↓
Candidate Interpretation
      ↓
Hard Schema Validation / Admission
      ↓
Admitted Intent
      ↓
Resolution
      ↓
Context / State Reconciliation
      ↓
Deterministic Trust
      ↓
EAG / Capability / Action Selection
      ↓
Action Contract
      ↓
Execution
      ↓
Integration Adapter
      ↓
Enterprise System

The adapter may perform provider-specific validation, but provider validation does not replace canonical Noema validation.

External responses, events, errors, and provider metadata must likewise be validated before being admitted as structured canonical evidence or state observations.

⸻

8. Adapter and Capability

An adapter binds a canonical capability to a provider-specific implementation.

Capability
     │
     │ binding
     ▼
Integration Adapter
     │
     │ invokes
     ▼
Provider Operation

The provider operation is an implementation of the capability, not the capability definition itself.

A provider endpoint therefore does not automatically establish a canonical capability.

⸻

9. Adapter and Action

An Action is selected from established semantic capability and action definitions and is governed by an applicable Action Contract.

The canonical execution path is:

Intent
   ↓
Resolution
   ↓
Capability
   ↓
Action
   ↓
Trust
   ↓
Action Contract
   ↓
Execution
   ↓
Integration Adapter
   ↓
Enterprise System

The adapter must not bypass this chain.

⸻

10. Adapter Interface

Every adapter should expose a canonical interface independent of provider technology.

Conceptually:

Adapter
├── identify()
├── capabilities()
├── validate()
├── execute()
├── normalize()
├── mapError()
├── health()
└── reconcile()

The exact implementation may differ, but the semantics must remain consistent.

An adapter interface may additionally expose provider-specific operations where those operations have been explicitly registered as capabilities or recovery operations.

⸻

11. Adapter Identity

Every adapter must have a stable identity.

An adapter identity should distinguish:

adapter_id
provider
system
environment
tenant_scope
version

Provider names or URLs alone are insufficient because multiple adapter configurations may exist for the same provider.

⸻

12. Adapter Version

Adapters are versioned independently from capabilities, actions, contracts, and provider APIs.

For example:

Capability v2
Action v3
Action Contract v4
Adapter v7
Provider API v4

These versions represent different concerns.

Changing an adapter implementation must not silently redefine the semantic meaning of the capability or Action.

⸻

13. Provider Binding

A provider binding describes how a canonical capability or Action Contract maps to an external operation.

Conceptually:

Canonical Capability / Action Contract
        │
        ├── provider
        ├── system
        ├── operation
        ├── endpoint
        ├── protocol
        ├── authentication
        ├── request mapping
        └── response mapping

The binding must be explicit, scoped, provenance-aware, and versioned.

A provider endpoint is an implementation reference, not canonical semantic authority.

⸻

14. Protocol Translation

Adapters may translate between protocols such as:

REST
GraphQL
gRPC
SOAP
SQL
Message Queue
Event Stream
SDK
Internal RPC

Protocol translation must not alter canonical Action semantics.

Direct database interaction is permitted only when the enterprise has explicitly exposed the relevant operation as an approved and governed integration capability. An adapter must not use arbitrary SQL to bypass enterprise execution boundaries.

⸻

15. Request Translation

The adapter transforms a canonical Action Contract request into provider-specific input.

Canonical Request
        ↓
Canonical Contract Validation
        ↓
Provider Mapping Validation
        ↓
Provider Mapping
        ↓
Provider Request

Required transformations must be deterministic.

Provider mapping must not add undeclared consequential operations.

⸻

16. Response Translation

Provider responses must be normalized into canonical Noema representations.

Provider Response
        ↓
Provider Parsing
        ↓
Provider Schema Validation
        ↓
Normalization
        ↓
Canonical Evidence / Execution Result

Normalization must preserve information required for execution verification, evidence, reconciliation, recovery, and auditability.

A normalized response is not automatically authoritative for every claim it contains.

⸻

17. Lossless Translation

Adapters should avoid unnecessary information loss.

If provider-specific information affects:

* execution outcome
* error interpretation
* reconciliation
* auditability
* evidence
* recovery
* state determination

it should remain available through structured metadata or provider evidence.

Provider-specific data should remain scoped to the integration boundary unless it has canonical semantic value.

⸻

18. Authentication

Adapters may manage the technical interaction with enterprise authentication mechanisms.

Examples include:

OAuth 2.0
API Keys
mTLS
JWT
Service Accounts
Signed Requests
Enterprise SSO Tokens

Authentication credentials must remain outside canonical Action semantics.

Authentication establishes the technical identity used for a provider interaction. It does not by itself establish business authorization.

⸻

19. Authorization Context

Adapters may propagate authorization context but must not invent authorization decisions.

Conceptually:

Enterprise Authorization / Trust Conditions
                ↓
         Action Contract
                ↓
             Adapter
                ↓
     Provider Authorization

Technical authorization, policy authorization, and business authorization remain distinct concerns.

A provider may independently enforce technical or business authorization, but the adapter must report the resulting condition rather than reinterpret it as a Noema Trust decision.

⸻

20. Credential Isolation

Provider credentials must be isolated from:

* model context
* user-visible responses
* Intent state
* Action payloads
* graph descriptions
* ordinary logs
* Operational Memory

Credentials should be accessed only by the adapter or dedicated secure infrastructure.

The model must not receive credentials or direct enterprise access merely because it is assisting with Intent interpretation or planning.

⸻

21. Tenant Isolation

Where Noema serves multiple enterprises or tenants, adapters must preserve tenant boundaries.

A request belonging to Tenant A must never accidentally execute through Tenant B’s:

* credentials
* configuration
* environment
* resource scope
* provider binding
* graph scope

Tenant identity must therefore be explicit in adapter resolution.

⸻

22. Environment Isolation

Adapters must distinguish environments such as:

development
staging
production
sandbox

A production Action must never accidentally resolve to a non-production adapter.

Environment is part of the execution binding and must be preserved in audit and provenance.

⸻

23. Resource Resolution

Adapters may resolve canonical Resource references into provider-specific identifiers.

For example:

Noema Resource
     ↓
Canonical Resource ID
     ↓
Adapter Mapping
     ↓
Provider Resource ID

Resource resolution must preserve:

* tenant scope
* organization scope
* environment
* resource identity
* authority
* resolution provenance

An adapter must not silently substitute a different resource.

⸻

24. Request Validation

Adapters should validate provider-specific requirements before invocation.

Examples:

* required fields
* field formats
* identifier formats
* supported operations
* provider limits
* schema constraints
* environment compatibility
* provider-specific preconditions

Provider validation supplements, rather than replaces, canonical Action Contract validation.

⸻

25. Contract Enforcement

Adapters must execute only requests that conform to the applicable Action Contract.

The adapter must not expand a request beyond the contract.

For example, if a capability permits:

retrieve_account_balance

the adapter must not interpret that request as permission to:

modify_account
transfer_funds
close_account

The adapter cannot grant itself additional capabilities.

⸻

26. Idempotency

Adapters must support idempotency where the underlying operation can produce externally visible side effects.

An adapter should preserve:

idempotency_key
execution_id
provider_request_id

where supported.

Idempotency is an execution property. It is not authorization, Trust, or proof of business success.

⸻

27. Duplicate Execution

Network uncertainty can produce:

request sent
      ↓
provider executed
      ↓
response lost

The adapter must not automatically assume that a missing response means the operation failed.

It must preserve uncertainty and support provider-specific reconciliation where possible.

⸻

28. Timeout Semantics

A timeout represents an inability to establish the result within the required time.

It does not automatically mean:

FAILED

The execution state may instead become:

UNKNOWN

until reconciliation establishes what happened.

A timeout is therefore an execution condition, not an authoritative business outcome.

⸻

29. Error Mapping

Provider errors must be mapped into canonical execution error categories.

For example:

Provider 401 → AUTHENTICATION_ERROR
Provider 403 → AUTHORIZATION_ERROR
Provider 404 → RESOURCE_NOT_FOUND
Provider 409 → CONFLICT
Provider 429 → RATE_LIMITED
Provider 5xx → PROVIDER_ERROR
Timeout     → OUTCOME_UNKNOWN

Mappings must be explicit and versioned.

A provider error classification must not be confused with a Trust outcome.

⸻

30. Error Preservation

Normalization must not destroy the original provider error.

A canonical error should retain sufficient provider evidence for:

* debugging
* audit
* support
* recovery
* reconciliation

Conceptually:

Canonical Error
├── category
├── retryability
├── provider_code
├── provider_message
├── provider_request_id
└── raw_evidence_reference

Sensitive provider data must still be protected.

⸻

31. Retry Responsibility

Adapters may implement technical retries for transport-level failures when explicitly configured.

Retries must not blindly repeat externally visible operations.

Retryable Transport Failure
        ↓
Idempotency / Execution-State Check
        ↓
Bounded Retry

Business-level retry decisions belong to the execution and policy model.

A technical adapter retry must not become an implicit business retry.

⸻

32. Retry Boundaries

Retry behavior must be explicit about:

* maximum attempts
* backoff
* retryable conditions
* idempotency requirements
* deadline
* cancellation
* provider limits
* reconciliation requirements

An adapter must not create an infinite retry loop.

After an uncertain side effect, reconciliation takes precedence over blind repetition.

⸻

33. Rate Limits

Adapters must respect provider rate limits.

Rate limiting may require:

* request throttling
* backoff
* concurrency limits
* provider quotas
* tenant quotas

Rate limiting must not be interpreted as an authorization decision.

⸻

34. Provider Availability

An adapter should expose operational availability information where possible.

Examples:

AVAILABLE
DEGRADED
UNAVAILABLE
UNKNOWN

Provider health must not be confused with:

* capability existence
* authorization
* Action eligibility
* execution success
* enterprise business state

A system may be temporarily unavailable while still providing the capability.

⸻

35. Capability Availability

The adapter may provide evidence about whether a provider capability is currently usable.

This can depend on:

* provider status
* configuration
* credentials
* environment
* feature flags
* tenant configuration
* API version

Availability must remain distinguishable from semantic capability existence.

Current availability may be UNKNOWN and may require State Reconciliation.

⸻

36. State Reconciliation

Adapters are an important source of observations used by State Reconciliation.

For example:

Enterprise System
       ↓
Provider Observation
       ↓
Hard Schema Validation / Admission
       ↓
State Reconciliation
       ↓
Reconciled Facts / Fact Status
       ↓
Trust / Execution / Verification

Reconciliation may establish whether:

* an operation occurred
* a resource exists
* a capability remains available
* a provider state changed
* a previous execution completed
* a provider response conflicts with another authoritative source

The adapter provides observations and reconciliation mechanisms. It does not independently establish enterprise truth.

⸻

37. Fact Status

Adapter observations must not be confused with Fact Status.

Fact Status is distinct from:

* Evidence
* Context
* provider response
* Execution Status
* Outcome
* enterprise Business State

Canonical Fact Status values include:

VERIFIED
UNVERIFIED
STALE
CONFLICTED
UNKNOWN

An adapter response can provide evidence supporting a Fact Status, but merely receiving a response does not automatically make every claim in that response VERIFIED.

⸻

38. Authority and Freshness

Adapter data must preserve the distinction between:

Source
Authority
Freshness
Validity

A recent provider response is not automatically authoritative for every claim.

Likewise, an authoritative source may provide stale information.

Authority and freshness are therefore evaluated according to the specific claim, resource, scope, and time semantics.

Recency alone does not establish truth.

⸻

39. Observability

Adapters must produce sufficient telemetry to reconstruct technical execution behavior.

Relevant information includes:

execution_id
intent_version
action_id
capability_id
adapter_id
provider
system
environment
request_id
provider_request_id
latency
status
error_category
retry_count
timestamp

Sensitive payloads must not be logged indiscriminately.

⸻

40. Correlation

Adapter operations must preserve correlation identifiers across boundaries.

Conceptually:

Intent ID
   ↓
Intent Version
   ↓
Action Instance ID
   ↓
Execution ID
   ↓
Adapter Request ID
   ↓
Provider Request ID

This enables end-to-end tracing and causal reconstruction.

⸻

41. Auditability

Adapter execution must produce sufficient evidence to establish:

* which Intent version was involved
* which Action and Contract were used
* which adapter was selected
* which adapter version was used
* which provider was contacted
* which operation was invoked
* which environment and tenant scope applied
* when invocation occurred
* what response, error, or uncertainty resulted

Audit records must not expose secrets.

⸻

42. Evidence Production

Adapters are an important source of execution evidence.

Examples include:

* provider response
* provider request identifier
* provider event
* provider status
* provider error
* acknowledgement
* timeout
* status lookup
* reconciliation response

Adapter-produced evidence must preserve provenance and integrity metadata.

Evidence supports reasoning; it does not automatically become enterprise truth.

⸻

43. Reconciliation

Adapters should support reconciliation when provider state cannot be established from the immediate response.

Examples:

check_operation_status
lookup_transaction
lookup_resource
retrieve_provider_event
retrieve_operation_history

Reconciliation is particularly important after:

* timeouts
* network failures
* lost responses
* duplicate delivery
* asynchronous execution
* conflicting provider observations

Unknown must not be silently converted into success or failure.

⸻

44. Recovery Support

An adapter may expose provider-specific recovery operations.

For example:

check_operation_status
retrieve_operation_result
cancel_operation
refresh_resource

Recovery operations must themselves be represented through bounded capabilities and applicable Action Contracts.

An adapter must not invent a compensating or recovery operation merely because an error occurred.

⸻

45. Provider Events

Where providers expose events, adapters may translate them into canonical Noema Events or evidence.

Provider Event
      ↓
Adapter
      ↓
Schema Validation / Admission
      ↓
Canonical Event / Evidence
      ↓
State Reconciliation / Execution / Graph

The adapter must preserve event provenance.

A provider event is an observation of an occurrence. It is not automatically the authoritative current business state.

⸻

46. Event Ordering

Provider events may arrive:

* late
* duplicated
* out of order
* missing
* after timeout

Adapters and downstream execution logic must therefore not assume delivery order unless the provider contract guarantees it.

Ordering semantics must be explicit where they affect reconciliation or execution.

⸻

47. Schema Evolution

Provider schemas change over time.

Adapters isolate these changes from canonical Noema semantics.

Provider API v1
      ↓
Adapter v1
Provider API v2
      ↓
Adapter v2
Canonical Capability
        ↑
Stable semantic boundary

Breaking provider changes should produce explicit adapter version changes or another explicitly governed compatibility mechanism.

⸻

48. Backward Compatibility

Where possible, adapters should support compatible provider changes without changing canonical capability semantics.

Backward compatibility must never be achieved by silently altering request or response meaning.

Semantic compatibility is more important than transport compatibility.

⸻

49. Adapter Composition

An adapter may depend on other technical adapters.

For example:

Capability Adapter
      ↓
Authentication Adapter
      ↓
Transport Adapter
      ↓
Provider

Composition must remain explicit.

A composed adapter chain must preserve the same tenant, environment, credential, contract, and execution boundaries.

⸻

50. Adapter Dependencies

Dependencies may include:

* credential provider
* identity provider
* network gateway
* secret manager
* schema registry
* provider SDK
* event transport
* reconciliation service

Dependencies must be versioned and observable where they materially affect execution.

⸻

51. Adapter Configuration

Configuration should be externalized from adapter logic where practical.

Configuration may define:

* endpoint
* credentials reference
* timeouts
* retry policy
* rate limits
* environment
* tenant scope
* provider version
* feature flags
* resource mappings

Configuration changes must be auditable where they affect execution semantics.

Configuration does not itself create capability, permission, or authorization.

⸻

52. Adapter Registration

Adapters must be registered before becoming eligible for execution.

Registration should establish:

adapter_id
provider
system
environment
tenant_scope
supported_capabilities
version
health
configuration
credentials_reference

Unregistered adapters must not be selected for execution.

Registration establishes integration availability metadata; it does not independently establish Trust or authorization.

⸻

53. Adapter Discovery

Noema may discover candidate adapters through:

* configuration
* integration metadata
* enterprise APIs
* provider documentation
* administrative setup
* controlled discovery mechanisms

Discovery produces candidate integration knowledge.

It does not automatically establish an executable adapter.

Canonical registration requires deterministic validation of:

* identity
* provider/system binding
* scope
* ownership
* provenance
* version
* capability bindings
* configuration
* lifecycle
* applicable credentials reference

⸻

54. Adapter Selection

Adapter selection must be deterministic after canonical inputs are established.

Selection may consider:

* capability
* Action Contract
* tenant
* organization
* environment
* resource
* provider
* availability
* version
* policy
* credential scope
* graph constraints
* integration compatibility

The model must not arbitrarily select an adapter at execution time.

If multiple adapters remain materially ambiguous after deterministic rules, the system must not guess. The appropriate control path may be clarification, escalation, or an explicitly defined non-execution state.

⸻

55. Multiple Adapters

Multiple adapters may implement the same capability.

For example:

Capability: retrieve_statement
    ├── Adapter A → Provider A
    ├── Adapter B → Provider B
    └── Adapter C → Internal System

Selection must follow explicit graph, policy, environment, tenant, capability, and semantic-compatibility constraints.

The existence of multiple adapters does not imply that they are interchangeable.

⸻

56. Failover

Failover between adapters must not be automatic merely because the primary adapter fails.

The alternative adapter must:

* support the same canonical capability
* satisfy the applicable Action Contract
* be valid for the resolved resource
* be authorized
* satisfy applicable policy
* be valid for the environment
* preserve required semantics
* satisfy tenant and organizational scope
* have appropriate availability
* preserve idempotency and reconciliation requirements

Failover is an execution decision, not merely a network decision.

A failed adapter does not automatically make another adapter eligible.

⸻

57. Semantic Equivalence

Two adapters may implement the same capability only if their outputs and behavior satisfy the canonical capability semantics.

Different provider APIs do not necessarily provide semantically equivalent operations.

The adapter registry must therefore distinguish:

same endpoint

from:

same capability

Semantic equivalence must be established through explicit capability and contract definitions, not inferred from similar API names.

⸻

58. Adapter Isolation

Provider-specific logic must remain isolated.

The rest of Noema should not need to know:

* provider endpoint format
* provider SDK types
* provider-specific status codes
* provider authentication details
* provider-specific pagination

unless such information is explicitly exposed as canonical execution evidence or integration metadata.

⸻

59. No Provider Leakage

Canonical Noema objects must not become polluted with provider-specific fields merely because an adapter requires them.

Provider-specific metadata should remain within the integration boundary unless it has canonical semantic value.

Canonical semantics must not become dependent on a provider’s internal vocabulary.

⸻

60. Adapter Security

Adapters are security-sensitive components because they sit directly on enterprise execution boundaries.

They must protect:

* credentials
* tokens
* secrets
* provider endpoints
* resource identifiers
* request payloads
* response payloads
* execution metadata

Security failures at the adapter boundary can become enterprise execution failures.

The model must not obtain direct credentials or direct provider access merely by influencing adapter input.

⸻

61. Secret Management

Adapters should reference secrets rather than embedding them.

Conceptually:

Adapter Configuration
       │
       └── secret_reference
                ↓
          Secret Manager
                ↓
             Credential

Secrets must not become part of:

* graph nodes
* Intents
* Action Contracts
* Context
* model context
* ordinary audit records

⸻

62. Input Sanitization

Adapter inputs must be validated and sanitized before reaching external systems.

This protects against:

* malformed requests
* injection attacks
* unexpected provider behavior
* invalid identifiers
* unsafe parameter propagation

Canonical validation remains the first boundary; adapter validation is provider-specific defense in depth.

⸻

63. Output Sanitization

Provider responses must be normalized before entering downstream Noema systems.

Sensitive provider fields should be filtered or classified appropriately.

The model should receive only information that is permitted and necessary for its role.

Provider output must not be treated as authoritative merely because it was returned by a connected system.

⸻

64. Cancellation

Adapters must support cancellation where the provider protocol allows it.

Cancellation must distinguish:

request cancelled before provider execution

from:

request cancelled after provider execution began

Cancellation does not necessarily establish business-state outcome.

If cancellation status is uncertain, State Reconciliation may be required.

⸻

65. Deadlines

Adapter requests should operate within explicit execution deadlines.

Deadlines should propagate through:

Execution
   ↓
Adapter
   ↓
Transport
   ↓
Provider

The adapter must not extend execution indefinitely.

A deadline expiration does not automatically establish business failure.

⸻

66. Concurrency

Adapters may enforce provider-specific concurrency constraints.

Examples:

* maximum concurrent requests
* per-tenant limits
* per-resource serialization
* provider connection pools

Concurrency controls must not alter semantic execution ordering unless explicitly required by the capability or provider contract.

⸻

67. Ordering

Some provider operations require ordering guarantees.

Where ordering is semantically required, the adapter must enforce or preserve it.

Where ordering is not required, the adapter should not impose unnecessary serialization.

Ordering requirements belong to explicit execution or provider semantics, not adapter intuition.

⸻

68. Pagination

Adapters may translate provider pagination into canonical retrieval semantics.

Provider-specific pagination mechanisms such as:

* cursor
* offset
* page number
* continuation token

must remain implementation details unless exposed through the canonical contract.

Pagination must preserve completeness and continuation semantics where they affect the canonical result.

⸻

69. Partial Results

Providers may return partial results.

Adapters must distinguish:

COMPLETE
PARTIAL
EMPTY
ERROR
UNKNOWN

A partial result must not silently become a complete canonical result.

Where completeness cannot be established, the result must retain that uncertainty.

⸻

70. Data Freshness

Adapter responses should preserve freshness information when relevant.

For example:

retrieved_at
provider_updated_at
source_version
resource_version

This is especially important for read-oriented capabilities.

Noema must not represent stale provider data as current without appropriate semantics and, where necessary, State Reconciliation.

⸻

71. Read Operations

Read-oriented adapters retrieve enterprise information without changing business state.

Phase 1 examples include:

retrieve_account_balance
retrieve_statement
search_transactions
calculate_spending_summary

These operations can still be consequential because they may expose protected financial or personal information.

They therefore still require appropriate:

* identity
* scope
* permissions
* policy
* Trust
* evidence
* data-boundary controls

Read-only does not mean consequence-free.

⸻

72. Write Operations

Write-capable adapters may support operations that change enterprise state.

Such adapters require stronger guarantees around:

* authorization
* idempotency
* policy
* auditability
* reconciliation
* recovery
* verification
* concurrency
* confirmation where required by the applicable control model

The existence of an adapter does not itself authorize a write.

Enterprise systems remain authoritative for the resulting business state.

⸻

73. Adapter Testing

Adapters should be tested against:

* contract tests
* provider integration tests
* schema compatibility tests
* error mapping tests
* timeout tests
* retry tests
* idempotency tests
* reconciliation tests
* security tests
* tenant isolation tests
* environment isolation tests
* partial-result tests
* semantic-equivalence tests

Tests should verify canonical semantics, not merely HTTP success.

⸻

74. Contract Testing

A contract test verifies that an adapter continues to satisfy the canonical capability and Action Contract.

Conceptually:

Canonical Contract
       ↓
Adapter
       ↓
Provider
       ↓
Observed Result
       ↓
Contract Verification

Provider success alone is insufficient.

The test must establish that the provider interaction preserves the semantics required by the canonical contract.

⸻

75. Adapter Lifecycle

Adapters have a lifecycle:

DISCOVERED
REGISTERED
VALIDATED
ACTIVE
DEGRADED
DISABLED
DEPRECATED
RETIRED

Lifecycle transitions must be explicit and auditable.

Lifecycle status is distinct from:

* capability existence
* provider health
* Trust outcome
* execution status
* business outcome

⸻

76. Adapter Deprecation

An adapter may be deprecated when:

* provider API is retiring
* security mechanism is obsolete
* capability binding is superseded
* provider integration is no longer supported

Deprecation must not silently invalidate historical executions.

Historical adapter versions must remain identifiable.

⸻

77. Adapter Retirement

A retired adapter must not receive new executions.

Historical references must remain resolvable enough to reconstruct prior execution behavior.

Historical Execution
      ↓
Retired Adapter Version

A healthy adapter process does not prove that the provider operation is available.

Likewise, provider availability does not establish that an Action is authorized or executable.

Adapter drift occurs when the provider changes behavior without the adapter’s canonical mapping being updated.

Examples:

* schema changed
* status semantics changed
* endpoint behavior changed
* authentication changed
* field meaning changed
* provider capability removed
* error semantics changed
* event semantics changed

Drift detection must feed integration validation and graph evolution.

82. Adapter and Trust

* available integration
* environment
* provider
* credential scope
* capability binding
* operational status
* integration policy
* current state

Canonical Trust outcomes remain:

EXECUTE
CLARIFY
ESCALATE
REJECT

Adapter states such as UNAVAILABLE, UNKNOWN, or DEGRADED are not Trust outcomes. They are integration or execution conditions that may contribute to a Trust or control decision.

Historical adapter records provide provenance and operational history; they do not become current truth merely by being stored.

* an Execution
* an adapter response
* a provider event

If a new execution is intentionally created from historical information, it is a new execution with a new identity and must pass the applicable current controls.

104. Final Definition

An Integration Adapter is the governed, versioned, scoped, and observable boundary through which Noema translates a validated, trusted, contract-bound canonical operation into provider-specific enterprise-system interaction and translates the resulting responses, errors, events, and observations back into structured Noema evidence.

The adapter isolates:

Noema's canonical execution model

from:

provider-specific implementation reality

while preserving:

identity
scope
authority
contracts
idempotency
evidence
provenance
errors
uncertainty
version
auditability
reconciliation

An adapter therefore does not decide:

* what the user wants
* whether an Intent is valid
* whether an action is trusted
* whether an action is authorized
* what the enterprise’s business truth is
* whether an unknown result should be guessed into success or failure

Its responsibility is narrower and fundamental:

Translate a validated, trusted, contract-bound Noema operation into a controlled enterprise-system interaction, preserve the exact execution lineage, and return sufficient structured evidence to establish what actually happened.

The core invariant is:

Canonical Semantics
        ↓
Action Contract
        ↓
Execution
        ↓
Integration Adapter
        ↓
Provider Operation
        ↓
Evidence
        ↓
Verification / Reconciliation
        ↓
Outcome

The adapter is therefore not merely an API client.

It is the governed boundary that allows Noema to execute across heterogeneous enterprise systems without surrendering canonical semantics, deterministic control, security boundaries, provenance, or enterprise ownership of business truth.
