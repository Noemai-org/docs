Action Graph

Status: Foundational
Version: 0.1
Domain: Architecture
Canonical Path: architecture/action-graph.md

⸻

1. Definition

The Action Graph is Noema’s explicit representation of the actions, dependencies, conditions, and execution relationships required to transform a trusted Intent into an executable outcome.

The Action Graph represents how an Intent can be fulfilled.

It does not determine whether the Intent is trusted.

Therefore:

* Intent defines what the Actor wants
* Validation establishes whether the Intent is structurally and semantically valid
* Trust establishes whether the Intent may proceed
* The Action Graph represents how the trusted Intent can be fulfilled
* Action Contracts define what each executable action permits and requires
* Execution performs the contracted actions
* Outcome records what actually happened

The Action Graph therefore sits primarily between Trust and Execution.

⸻

2. Core Principle

Noema must not reduce execution planning to an opaque sequence generated by a model.

An execution plan must be representable as explicit, inspectable structure.

Conceptually:

Trusted Intent
      ↓
Action Graph
      ↓
Action Contracts
      ↓
Execution
      ↓
Outcome

The graph makes dependencies and execution relationships explicit.

⸻

3. Why an Action Graph Exists

Many real-world Intents cannot be fulfilled by a single Action.

Example:

“Renew my card and send it to my current address.”

This may require:

Resolve Account
      ↓
Verify Card Eligibility
      ↓
Verify Delivery Address
      ↓
Request Card Renewal
      ↓
Confirm Renewal
      ↓
Initiate Delivery
      ↓
Verify Outcome

Some actions may execute sequentially.

Others may execute independently.

Some may depend on the result of previous actions.

Some may require approval before execution.

The Action Graph provides a canonical representation for these relationships.

⸻

4. Action Graph vs Intent

An Intent is not an Action Graph.

The Intent represents the Actor’s objective.

The Action Graph represents a possible operational realization of that objective.

For example:

Intent:
Replace my expired card.

may become:

Action Graph:
Check Card Status
        ↓
Check Replacement Eligibility
        ↓
Create Replacement Request
        ↓
Verify Request Accepted

The graph may change while the Intent remains the same.

Therefore:

Intent ≠ Action Graph

The graph is derived from the Intent and applicable capabilities.

⸻

5. Action Graph vs Plan

The Action Graph is the canonical structural representation.

A plan may contain additional execution strategy.

For example:

Action Graph:
A → B
A → C
B → D
C → D

An execution planner may determine:

Execute A
Parallel:
    B
    C
Then:
    D

The distinction is:

Action Graph

represents dependencies and permitted relationships.

Execution Plan

represents a concrete strategy for traversing those relationships.

Noema should avoid treating an LLM-generated plan as authoritative merely because it appears coherent.

⸻

6. Action Graph vs Workflow

A workflow is generally an operational process.

An Action Graph is a representation of the actions and dependencies required to fulfill an Intent.

A workflow may be:

Card Renewal Workflow

while the Action Graph for a particular Intent may contain only the actions relevant to that specific case.

Therefore:

Workflow = reusable process
Action Graph = Intent-specific execution structure

The exact relationship between reusable workflows and Action Graphs may be formalized separately.

⸻

7. Graph Model

Conceptually:

                 Intent
                   │
                   ▼
             Action Graph
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
       Action A  Action B  Action C
          │        │        │
          └────┬───┴────┬───┘
               ▼        ▼
             Action D
                │
                ▼
             Outcome

The graph consists primarily of:

* nodes
* dependencies
* conditions
* inputs
* outputs
* execution relationships
* failure semantics

⸻

8. Action Graph Node

An Action Graph node represents an action that may be evaluated for execution.

Conceptually:

ActionNode {
    id
    action
    inputs
    outputs
    capability
    contract
    preconditions
    postconditions
    dependencies
    constraints
    state
    provenance
}

The exact schema belongs to the architecture and action-contract specifications.

⸻

9. Action Identity

Every executable Action should have an explicit identity.

For example:

CARD_STATUS_CHECK
CARD_REPLACEMENT_REQUEST
DELIVERY_ADDRESS_LOOKUP
CARD_DELIVERY_REQUEST

An Action identity should not depend on natural-language descriptions generated by a model.

Human-readable descriptions may accompany an Action.

They should not replace its canonical identity.

⸻

10. Action Inputs

An Action may require explicit inputs.

Example:

CARD_REPLACEMENT_REQUEST
Inputs:
    account_id
    card_id
    replacement_reason
    delivery_address

Inputs should originate from:

* the Intent
* trusted context
* outputs of prior Actions
* explicitly permitted defaults
* authoritative external evidence

Inputs must not be invented merely to complete a graph.

⸻

11. Action Outputs

Actions may produce outputs that become inputs to downstream Actions.

Example:

VERIFY_CARD
    output:
        card_eligibility
        ↓
REQUEST_REPLACEMENT
    input:
        card_eligibility

Outputs should be explicitly typed where the relevant contract supports typed values.

⸻

12. Dependencies

A dependency establishes that one Action depends on another Action or condition.

Example:

A
↓
B

means:

B cannot execute until the dependency represented by A
has been satisfied according to the applicable contract.

A dependency must not be inferred merely from the visual ordering of nodes.

It must be explicitly represented.

⸻

13. Dependency Types

The canonical model may support several dependency relationships.

Examples include:

DATA_DEPENDENCY
ORDER_DEPENDENCY
CONDITION_DEPENDENCY
AUTHORIZATION_DEPENDENCY
APPROVAL_DEPENDENCY
RESOURCE_DEPENDENCY

The exact dependency taxonomy may evolve.

The important principle is that different dependency semantics should not be conflated.

⸻

14. Data Dependency

A data dependency exists when an Action requires output from another Action.

Example:

LOOKUP_CUSTOMER
      │
      │ customer_id
      ▼
FETCH_CUSTOMER_ACCOUNT

The second Action cannot construct its required input until the first Action provides it.

⸻

15. Ordering Dependency

An ordering dependency establishes required sequencing even when the downstream Action does not consume the upstream Action’s output.

Example:

REVOKE_OLD_TOKEN
      ↓
ISSUE_NEW_TOKEN

The new token should not be issued before the old token is revoked when the governing Action Contracts require that ordering.

⸻

16. Condition Dependency

An Action may depend on a condition established by another Action.

Example:

CHECK_ELIGIBILITY
      ↓
eligible = true
      ↓
RENEW_CARD

If:

eligible = false

the downstream Action must not execute.

The condition is part of the graph semantics.

⸻

17. Parallel Actions

Independent Actions may execute concurrently when the relevant contracts permit it.

Example:

             ┌── CHECK_ACCOUNT ──┐
             │                   │
VERIFY_USER ─┤                   ├── COMPLETE_REQUEST
             │                   │
             └── CHECK_CARD ────┘

The graph represents:

VERIFY_USER → CHECK_ACCOUNT
VERIFY_USER → CHECK_CARD
CHECK_ACCOUNT → COMPLETE_REQUEST
CHECK_CARD    → COMPLETE_REQUEST

Parallel execution must not be inferred solely because two Actions appear independent.

The execution layer must establish that parallelism is safe.

⸻

18. Sequential Actions

Actions requiring strict ordering must be represented explicitly.

Example:

A
↓
B
↓
C

The graph therefore establishes:

B depends on A
C depends on B

A planner or executor must not reorder these actions unless the governing semantics explicitly permit it.

⸻

19. Branching

An Action Graph may contain conditional branches.

Example:

CHECK_ELIGIBILITY
       │
   ┌───┴────┐
   │        │
eligible  ineligible
   │        │
   ▼        ▼
RENEW     STOP

The branch condition must be explicit.

Noema must not allow a model to silently select a branch based on an unstated assumption.

⸻

20. Convergence

Multiple branches may converge on a later Action.

Example:

          ┌── PATH A ──┐
START ────┤            ├── COMPLETE
          └── PATH B ──┘

The convergence condition must specify what is required before the downstream Action can execute.

⸻

21. Graph Acyclicity

The default Action Graph should be a directed acyclic graph.

Conceptually:

A → B → C

is valid.

Whereas:

A → B → C
↑       ↓
└───────┘

creates a cycle.

Cycles should not be permitted unless the architecture explicitly defines a bounded iterative execution construct.

This prevents uncontrolled execution loops.

⸻

22. Iteration

Some business processes legitimately require repetition.

For example:

Poll delivery status
      ↓
Is delivered?
   ↙       ↘
No         Yes
↓           ↓
Wait       Complete
↓
Poll again

This should not be represented as an unrestricted graph cycle.

Instead, iteration should be represented through an explicit bounded construct defining:

* iteration condition
* maximum attempts
* timeout
* delay
* termination condition
* failure behavior

⸻

23. Graph Preconditions

Each Action may define preconditions.

Example:

RENEW_CARD
Preconditions:
    card.status = ELIGIBLE
    actor.authorized = true
    delivery.address_verified = true

An Action whose preconditions are not satisfied cannot execute.

Preconditions may be evaluated by the Trust system, the execution consumer, or both depending on the Action Contract.

⸻

24. Graph Postconditions

Actions may define expected postconditions.

Example:

REQUEST_REPLACEMENT
Expected postcondition:
    replacement_request.status = CREATED

Postconditions are useful for verifying whether execution produced the expected state.

They do not make Noema the authoritative owner of external business state.

⸻

25. Action Contract Boundary

Each executable Action should resolve to an Action Contract before execution.

Conceptually:

Action Graph Node
       ↓
Action Contract
       ↓
Consumer
       ↓
Execution

The Action Graph determines the structural role of an Action.

The Action Contract determines the executable interface and obligations.

⸻

26. Capability Binding

An Action must bind to an appropriate capability.

Example:

Action:
CARD_REPLACEMENT_REQUEST
Capability:
card.replacement.create

Capability answers whether a system exposes the required operation.

It does not itself establish permission.

Therefore:

Capability ≠ Authorization

⸻

27. Authorization Within the Graph

An Action may have authorization requirements.

Example:

TRANSFER_FUNDS
Authorization:
    Actor may transfer from source account

The graph may represent the dependency:

Authorization Check
        ↓
Transfer Action

But the Action Graph does not replace the Trust Engine.

Authorization remains part of the Trust boundary.

⸻

28. Approval Dependencies

Some Actions require human or organizational approval.

Example:

CREATE_TRANSFER
       ↓
WAIT_FOR_APPROVAL
       ↓
EXECUTE_TRANSFER

The graph may explicitly represent the approval dependency.

Approval is evidence of a required governance condition.

It does not eliminate the need for re-evaluation.

⸻

29. Confirmation Dependencies

An Action may require explicit Actor confirmation.

Example:

DELETE_ACCOUNT
       ↓
WAIT_FOR_CONFIRMATION
       ↓
EXECUTE_DELETE

Confirmation must be represented explicitly where required.

Noema must not interpret conversational continuation as confirmation unless the governing semantics establish that behavior.

⸻

30. Graph and Trust

The Action Graph does not bypass Trust.

The canonical relationship is:

Intent
  ↓
Validation
  ↓
Trust
  ↓
Action Graph
  ↓
Action Contracts
  ↓
Execution

Depending on implementation, graph construction may begin before Trust is complete.

However, no Action may cross the execution boundary without satisfying the applicable Trust requirements.

⸻

31. Graph Construction Before Trust

Noema may construct a candidate Action Graph while an Intent is still being evaluated.

For example:

Intent
  ↓
Candidate Action Graph
  ↓
Trust Evaluation

This can support planning and analysis.

The candidate graph is not therefore executable.

The distinction must remain explicit:

Candidate Graph ≠ Executable Graph

⸻

32. Graph Authorization

An Action Graph should not itself be interpreted as authorization.

For example:

Graph contains:
TRANSFER_FUNDS

does not mean:

Actor is authorized to transfer funds.

The graph represents a possible execution structure.

Trust and Action Contracts establish whether the individual Actions may actually execute.

⸻

33. Graph Validity

An Action Graph should itself be structurally valid before execution.

Validation may establish:

* all required nodes exist
* node identities are valid
* dependencies reference valid nodes
* graph dependencies are coherent
* required inputs are available
* cycles are prohibited or explicitly bounded
* conditions are well formed
* Action Contracts are resolvable
* capability references are valid

⸻

34. Graph Validation Result

Conceptually:

ActionGraphValidationResult {
    status
    errors
    warnings
    unresolved_dependencies
}

Possible statuses include:

VALID
INVALID
INCOMPLETE
UNKNOWN

The same deterministic principles used elsewhere in Noema apply.

Unknown must not silently become valid.

⸻

35. Graph Immutability During Execution

Once execution begins, the executed graph should not be silently mutated.

If the Intent or material execution conditions change, Noema should create an explicit transition.

Conceptually:

Graph Version 1
      ↓
material change
      ↓
Re-evaluation
      ↓
Graph Version 2

The relationship between graph versions must remain auditable.

⸻

36. Graph Versioning

An Action Graph should have an explicit version or evaluation identity.

Conceptually:

Intent Version: 7
Graph Version: 3
Trust Evaluation: 14

This permits Noema to reconstruct which graph was authorized for execution.

⸻

37. Graph Provenance

The Action Graph should record why each significant Action exists.

Provenance may include:

* source Intent
* Intent version
* Action identity
* capability source
* applicable policy
* dependency source
* evidence references
* graph generation/evaluation ID
* graph version
* timestamp

This supports auditability without requiring exposure of private model reasoning.

⸻

38. Model-Generated Graphs

LLMs may propose Action Graphs.

For example:

LLM
 ↓
Candidate Action Graph
 ↓
Deterministic Graph Validation
 ↓
Trust / Contract Validation
 ↓
Executable Graph

The LLM must not be the authoritative source of graph validity.

A model-generated graph is a proposal until it satisfies the deterministic requirements.

⸻

39. No Hidden Actions

An executable graph must not contain implicit actions that are absent from the graph representation.

For example, if the graph says:

TRANSFER_FUNDS

but execution silently performs:

LOOKUP_ACCOUNT
CHECK_BALANCE
CREATE_AUDIT_RECORD
SEND_NOTIFICATION

those additional operations must either be:

* part of the Action Contract,
* represented as explicit graph nodes,
* or otherwise explicitly defined as contractually required execution behavior.

Noema must avoid hidden execution semantics.

⸻

40. No Arbitrary Model Tool Calls

A model must not bypass the Action Graph by directly issuing arbitrary tool calls for consequential Actions.

The canonical path remains:

Intent
 ↓
Trust
 ↓
Action Graph
 ↓
Action Contract
 ↓
Consumer
 ↓
Execution

Tool use is an implementation mechanism, not an authority model.

⸻

41. Action Graph and Existing Systems

The Action Graph does not replace enterprise systems.

It coordinates Actions against existing capabilities.

Example:

Noema Action Graph
       │
       ├── CRM capability
       ├── Identity capability
       ├── Payment capability
       └── Notification capability

The external systems remain authoritative for their respective business domains.

⸻

42. Action Graph and Business State

The graph may depend on business state.

For example:

Account.status = ACTIVE

may be required before an Action executes.

Noema may obtain that fact from the authoritative system.

It should not silently claim ownership of that state.

⸻

43. External State Can Change

An Action Graph may become invalid between construction and execution.

Example:

T1:
Account = ACTIVE
T2:
Account = SUSPENDED
T3:
Execute Action

The execution consumer may reject the Action.

This is not necessarily evidence that the original graph was malformed.

It demonstrates that external business state is dynamic.

⸻

44. Time-of-Check / Time-of-Use

The graph must account for TOCTOU conditions.

Conceptually:

Validate
   ↓
Trust
   ↓
Contract
   ↓
Execute

does not imply:

conditions at Validate = conditions at Execute

Therefore consequential Action Contracts may require final authoritative checks at execution time.

⸻

45. Failure Propagation

Failures in one node may affect downstream nodes.

Example:

A
↓
B
↓
C

If B fails:

B = FAILED

then C should not automatically execute unless the graph explicitly defines a recovery path.

⸻

46. Failure Policies

An Action Graph may define failure behavior such as:

STOP
RETRY
COMPENSATE
SKIP
ESCALATE
CONTINUE

These semantics must be explicit.

A model must not invent recovery behavior during execution.

⸻

47. Retry

Retries must be bounded and contractually defined.

Conceptually:

Action
  ↓
FAILED
  ↓
Retry permitted?
  ├── No → FAILED
  └── Yes
       ↓
    Retry

Retry semantics should consider:

* maximum attempts
* timeout
* idempotency
* retryable failure classes
* backoff
* external system semantics

⸻

48. Idempotency

Actions that may be retried should define idempotency semantics where appropriate.

For example:

CREATE_PAYMENT

should not accidentally create multiple payments merely because Noema retries after an uncertain response.

Idempotency belongs primarily to the Action Contract and execution architecture, but the Action Graph must respect those semantics.

⸻

49. Compensation

Some multi-action executions may require compensating actions.

Example:

A → B → C
C fails
Compensation:
B_compensate
A_compensate

Compensation must never be assumed to be equivalent to rollback.

External systems may not support transactional rollback.

Compensation semantics must therefore be explicit.

⸻

50. Partial Execution

A graph may partially execute.

Example:

A → COMPLETED
B → COMPLETED
C → FAILED
D → NOT_STARTED

The resulting Intent outcome must distinguish:

* completed actions
* failed actions
* pending actions
* skipped actions
* unknown actions

Partial execution must not be silently represented as overall success.

⸻

51. Unknown Execution Outcome

An Action may produce an unknown result.

Example:

REQUEST_PAYMENT
      ↓
network timeout
      ↓
result unknown

Noema must not assume:

FAILED

if the external system may have successfully processed the request.

The graph and Action Contract should support explicit unknown outcomes where necessary.

⸻

52. Completion Conditions

Graph completion must be explicitly defined.

A graph is not necessarily complete merely because the final node returned a successful response.

Completion may require:

* all mandatory nodes completed
* required postconditions verified
* required external outcomes observed
* no unresolved mandatory branches
* no outstanding compensation requirements

The exact completion semantics belong to the relevant execution specification.

⸻

53. Graph Outcome

The Action Graph may produce an execution-level outcome such as:

COMPLETED
FAILED
PARTIALLY_COMPLETED
BLOCKED
WAITING
UNKNOWN

These outcomes must remain distinct from Trust state.

For example:

Trust State:
READY
Execution State:
FAILED

is valid.

⸻

54. Composite Actions

An Action Graph may contain Actions that themselves represent composite operations.

For example:

RENEW_CARD

may internally invoke multiple provider operations.

Whether those internal operations are represented as graph nodes depends on the Action Contract boundary.

The canonical requirement is that the abstraction boundary must be explicit.

⸻

55. Atomicity

The graph must distinguish whether a group of Actions is:

* atomic
* independently executable
* partially executable
* compensatable

Noema must not infer atomicity merely because Actions belong to the same Intent.

⸻

56. Composite Intent

A composite Intent may produce multiple related Action Graph components.

Example:

Intent:
"Close the account, transfer the remaining balance,
and notify me."
Graph:
Close Account
Transfer Balance
Send Notification

The graph must encode whether these Actions are:

* sequential
* parallel
* conditionally dependent
* atomic
* independently executable

The Actor’s Intent semantics must govern whether partial execution is permissible.

⸻

57. Partial Execution Must Be Explicit

If an Intent does not permit partial execution:

A = READY
B = BLOCKED
C = READY

must not result in:

Execute A
Execute C

simply because those nodes are individually executable.

The graph must respect the atomicity and partial-execution semantics of the Intent.

⸻

58. Graph State

Each node may have an execution state.

Conceptually:

NOT_READY
READY
EXECUTING
COMPLETED
FAILED
SKIPPED
BLOCKED
WAITING
UNKNOWN

The graph itself may also have an aggregate execution state.

The exact state model should remain separate from the Trust State Machine.

⸻

59. Trust State vs Graph State

These must not be conflated.

Example:

Trust:
READY
Graph:
READY
Execution:
NOT_STARTED

Later:

Trust:
READY
Graph:
EXECUTING
Execution:
EXECUTING

And finally:

Trust:
READY
Execution:
FAILED

Trust establishes eligibility.

Execution state establishes what happened operationally.

⸻

60. Graph Re-Evaluation

A material change may require the Action Graph to be re-evaluated.

Examples:

* capability disappears
* Action Contract changes
* required resource becomes unavailable
* policy changes
* Intent changes
* authorization changes
* dependency becomes invalid
* external state changes materially

Conceptually:

Action Graph
     ↓
Material Change
     ↓
Revalidation
     ↓
Trust Re-evaluation
     ↓
Graph Revision if required

⸻

61. Graph Invalidation

A graph should be considered invalid for execution when a material dependency no longer holds.

Example:

Graph:
Transfer → Notify
Transfer capability revoked

The graph may require revision before execution can continue.

Noema must not silently execute a stale graph.

⸻

62. Graph and Policy

Policies may affect graph construction.

Example:

Transfer > ₦10M
        ↓
Approval required

The resulting graph may contain:

Create Transfer
      ↓
Request Approval
      ↓
Execute Transfer

Policy determines the requirement.

The graph represents the resulting operational dependency.

⸻

63. Graph and Risk

Risk controls may add conditions or prohibit graph execution.

Example:

High-risk transfer
        ↓
Additional verification
        ↓
Approval
        ↓
Transfer

Risk policy therefore may alter the graph without becoming part of the graph’s authority model.

⸻

64. Graph and Human Intervention

Human intervention can be represented as an explicit graph dependency.

Example:

ACTION
  ↓
HUMAN_REVIEW
  ↓
CONTINUE

The graph should distinguish:

HUMAN_REVIEW_REQUIRED

from:

ACTION_FAILED

Human intervention is a legitimate execution state.

⸻

65. Graph and Clarification

Clarification normally occurs before an executable graph can be finalized when required information is missing.

Example:

Intent:
"Send the report to John."
Multiple Johns found.
Intent
  ↓
Clarification
  ↓
Resolved Intent
  ↓
Action Graph

Noema should not construct an executable graph by arbitrarily selecting one recipient.

⸻

66. Candidate vs Executable Graph

The architecture should preserve this distinction:

Candidate Action Graph
        ↓
Graph Validation
        ↓
Trust Evaluation
        ↓
Contract Validation
        ↓
Executable Action Graph

A candidate graph may contain unresolved dependencies.

An executable graph must satisfy the requirements necessary for execution.

⸻

67. Graph Determinism

For a given:

Intent
Context
Evidence
Capabilities
Policies
Action Contracts
Graph Rules
Versions

the resulting canonical graph should be deterministic where the architecture requires deterministic construction.

If multiple valid execution strategies exist, Noema may represent alternative candidate graphs or select among them using an explicitly defined policy.

The selection mechanism must not silently become arbitrary model behavior.

⸻

68. Graph Selection

Multiple graphs may fulfill the same Intent.

Example:

Intent:
Notify customer.
Possible capabilities:
Email
SMS
Push Notification

The selection mechanism may depend on:

* Actor preference
* available capability
* policy
* cost constraints
* delivery requirements
* context
* explicit Intent constraints

The selection criteria should be explicit.

⸻

69. Graph Optimization

Graph optimization may seek to improve:

* execution latency
* number of external calls
* resource consumption
* reliability
* cost
* parallelism

Optimization must not violate:

* Intent semantics
* Trust requirements
* Action Contracts
* policies
* authorization
* constraints
* atomicity
* safety boundaries

Optimization is subordinate to correctness and authority.

⸻

70. No Semantic Mutation Through Optimization

Graph optimization must not change what the Actor intended.

For example:

Intent:
Send an email and create an audit record.

An optimizer cannot remove the audit record merely because it reduces execution cost.

Graph optimization changes execution structure, not Intent semantics.

⸻

71. Graph Observability

Noema should be able to inspect:

* graph version
* node states
* dependency states
* selected capabilities
* Action Contracts
* execution timestamps
* failures
* retries
* compensation
* human interventions
* final outcome

This provides operational observability without requiring access to hidden model reasoning.

⸻

72. Graph Audit History

Significant graph changes should be auditable.

Example:

Graph v1
    ↓
Capability unavailable
    ↓
Graph invalidated
    ↓
Graph v2
    ↓
Alternative capability selected

The history should preserve why the graph changed.

⸻

73. Graph Provenance and Model Provenance

If an LLM proposed a graph, Noema may record:

generation_source = model
model_id
model_version
generation_timestamp

But the canonical authority remains:

deterministic validation
+
Trust
+
Action Contracts

Model provenance explains origin.

It does not establish permission.

⸻

74. Security Boundary

The Action Graph must not become an authority-escalation mechanism.

A malicious or compromised model must not be able to obtain additional capabilities simply by constructing a graph containing them.

Capability and authorization must remain independently verified.

⸻

75. Capability Discovery

Noema may discover available capabilities dynamically.

Conceptually:

Intent
   ↓
Required Action
   ↓
Capability Discovery
   ↓
Candidate Capabilities
   ↓
Capability Selection
   ↓
Action Graph

Discovered capabilities must still satisfy their applicable contracts and authorization requirements.

⸻

76. Consumer Validation

The execution consumer may reject an Action even after the graph has been validated.

Example:

Noema:
Graph valid
Trust ready
Contract valid
Consumer:
Precondition no longer satisfied

The consumer remains authoritative over execution-time business conditions within its domain.

⸻

77. Graph Does Not Guarantee Success

An executable graph establishes an authorized execution structure.

It does not guarantee:

Execution = SUCCESS

External systems can fail.

Resources can change.

Networks can fail.

Business state can change.

Therefore:

Executable Graph ≠ Successful Outcome

⸻

78. Canonical Action Graph Flow

The conceptual lifecycle is:

Resolved Intent
       ↓
Candidate Actions
       ↓
Candidate Action Graph
       ↓
Graph Validation
       ↓
Trust Evaluation
       ↓
Capability Binding
       ↓
Action Contract Binding
       ↓
Executable Action Graph
       ↓
Execution
       ↓
Postcondition Verification
       ↓
Outcome

At any stage, Noema may need to:

CLARIFY
WAIT
BLOCK
REPLAN
ESCALATE
FAIL

as explicitly defined by the applicable semantics.

⸻

79. State Transition Principle

An Action Graph state may change only because of:

* a defined event
* a dependency transition
* a contract result
* a material condition change
* deterministic re-evaluation

It must not change merely because:

* a model is more confident
* a prompt was reformulated
* a model generated a different plan
* a retry happened without a defined retry policy

⸻

80. Action Graph Invariants

Invariant 1

The Action Graph represents execution structure, not Intent meaning.

Invariant 2

The Action Graph does not grant authorization.

Invariant 3

Every executable Action must resolve to an explicit capability and applicable Action Contract.

Invariant 4

Dependencies must be explicit.

Invariant 5

Conditional branches must have explicit conditions.

Invariant 6

Unknown mandatory conditions must not be treated as satisfied.

Invariant 7

A candidate graph is not automatically executable.

Invariant 8

Graph optimization must not alter Intent semantics.

Invariant 9

Partial execution must be explicitly permitted.

Invariant 10

Retries must respect defined retry and idempotency semantics.

Invariant 11

External business systems remain authoritative for their business state.

Invariant 12

Material graph changes must be auditable.

Invariant 13

A stale graph must not silently cross the execution boundary.

Invariant 14

Execution failure does not imply that the original Trust decision was invalid.

Invariant 15

Graph structure must never be used to bypass Trust, authorization, policy, or Action Contract requirements.

⸻

81. Canonical Mental Model

The Action Graph can be reduced to five questions:

1. What Actions are required to fulfill the Intent?
2. What does each Action depend on?
3. Which capabilities and contracts can perform those Actions?
4. Under what conditions may each Action execute?
5. What happens if an Action succeeds, fails, or produces an unknown result?

This produces:

Intent
  ↓
Actions
  ↓
Dependencies
  ↓
Contracts
  ↓
Execution
  ↓
Outcome

83. The Fundamental Boundary

The Action Graph is the structural bridge between:

"May this Intent proceed?"

and:

"How will the permitted Action actually be performed?"

Therefore:

Trust
  ↓
Execution Eligibility
  ↓
Action Graph
  ↓
Action Contract
  ↓
Execution

The graph must never become a substitute for Trust.

⸻

84. Final Definition

The Action Graph is Noema’s explicit, inspectable representation of the Actions, dependencies, conditions, capabilities, and execution relationships required to fulfill a trusted Intent.

Its central invariant is:

Noema does not execute an opaque model-generated plan. It executes explicit Actions governed by explicit dependencies, capabilities, contracts, authorization, and execution conditions.
